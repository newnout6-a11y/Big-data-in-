## 1. Что мы построили (5 мин)

### Постановка задачи

Дано: ~575 научных статей и методичек по применению Big Data в химии (PDF и DOCX). Объём — десятки тысяч страниц на русском и английском.

**Проблема**: студент или преподаватель не может прочитать всё. Поиск по ключевым словам (Ctrl+F) находит только точные совпадения, не понимает синонимов, не работает кросс-язычно.

**Решение**: семантический поиск по смыслу + LLM, которая на основе найденных кусков пишет ответ на русском со ссылками на источник.

### Что получилось

Web-приложение `http://localhost:8501`, в нём:

- **Поле вопроса** на русском языке.
- **Селектор кейса** (15 тематик: токсичность, катализ, выход реакции, спектроскопия и т. д.).
- **Слайдер** — сколько фрагментов искать (3–10).
- **Кнопка «Найти ответ»**.

После нажатия:

1. Вопрос превращается в вектор из 768 чисел.
2. Qdrant находит N ближайших фрагментов из базы.
3. Фильтры выкидывают мусор (списки литературы, колонтитулы).
4. Groq LLaMA 3.3 70B пишет ответ на основе фрагментов.
5. В ответе появляются маркеры `[1]`, `[2]`, … — наведение мышью показывает реальную цитату.
6. Ниже — список источников с кликабельными ссылками на Google Scholar.

Плюс «Демо-режим» — тумблер, при котором используются заранее заготовленные ответы из `fallback_answers.py`. Страховка для защиты, если интернет/API упали.

## 2. Теория RAG — общая схема (15 мин)

### Что такое RAG

**RAG** = **R**etrieval-**A**ugmented **G**eneration — «генерация ответа с дополнением через поиск». Гибрид двух подходов:

1. **Retrieval (поиск)** — ищем релевантные куски в базе знаний по семантической близости.
2. **Generation (генерация)** — большая языковая модель (LLM) пишет ответ, опираясь только на найденные куски.

### Зачем нужен RAG

Чистая LLM (просто ChatGPT без базы) имеет три проблемы:

- **Галлюцинации**: модель не знает специфические данные и часто выдумывает факты с уверенным видом.
- **Устаревание**: знания зафиксированы в момент обучения. ChatGPT-3.5 не знает событий 2024 года.
- **Невозможность цитировать**: модель не может указать «в какой именно книге это написано».

RAG решает все три:

- Модель видит реальные тексты → меньше галлюцинаций.
- Базу можно обновлять без переобучения модели.
- В ответе можно проставить ссылки на конкретные куски.

### Схема работы

```
ПОЛЬЗОВАТЕЛЬ                        ВЕКТОРНАЯ БД                      LLM
    |                                     |                             |
    | вопрос: "Какая формула выхода?"    |                             |
    |--------+                            |                             |
            \|/                           |                             |
        [embedding-модель]                |                             |
            |                             |                             |
            | вектор(768)                 |                             |
            +---------------------------->|                             |
                                          |  cos-sim search             |
                                          |  top-K фрагментов           |
            +<----------------------------+                             |
            |                             |                             |
            | контекст (5 фрагментов)     |                             |
            +--------------------------------------------------------->|
                                                                       |
                                                          [LLaMA 3.3 70B]
                                                                       |
            +<---------------------------------------------------------+
            |
            | ответ + маркеры [1] [3] [5]
   ПОЛЬЗОВАТЕЛЬ
```

Три «двигателя» в RAG:

1. **Embedding-модель** — превращает текст в вектор.
2. **Векторная БД** — хранит векторы и быстро находит похожие.
3. **LLM** — пишет связный ответ из найденных фрагментов.

### Почему это работает

Ключевая идея: **семантически близкие тексты дают близкие векторы в 768-мерном пространстве**.

Пример: фразы «формула выхода реакции» и «reaction yield formula» — на разных языках, но обе модель кодирует в почти одинаковые векторы (расстояние ~0.05). Поэтому русский вопрос находит английский фрагмент.

«Расстояние» = косинусное сходство (см. раздел 4).

## 3. Эмбеддинги: multilingual-e5-base (10 мин)

### Что такое эмбеддинг

**Эмбеддинг** = числовой вектор, описывающий смысл текста. У нас вектор имеет 768 измерений (стандарт для BERT-подобных моделей).

```
"формула выхода реакции"  →  [0.12, -0.45, 0.77, ..., 0.03]   (768 чисел)
"reaction yield formula"  →  [0.13, -0.44, 0.76, ..., 0.04]
"кошка спит на диване"    →  [-0.81, 0.22, -0.33, ..., 0.91]
```

Первые два вектора близки (cosine similarity ≈ 0.92), третий далеко (≈ 0.05). Это и есть «семантика в числах».

### Какую модель используем

`intfloat/multilingual-e5-base` — открытая модель из Hugging Face, тренированная на 100+ языках. Размер: 278 MB, 768-мерные векторы.

Альтернативы и почему мы их не взяли:

| Модель | Плюсы | Минусы |
|---|---|---|
| `multilingual-e5-base` ✓ | бесплатно, локально, RU+EN | 278 MB, ~50ms/запрос |
| `text-embedding-ada-002` (OpenAI) | сильная, 1536-dim | $0.0001/1K tokens, REST-вызов, нужен прокси из РФ |
| `multilingual-e5-large` | точнее на 2-3% | 1.1 GB, в 2× медленнее |
| `paraphrase-multilingual-MiniLM` | 110 MB, быстрая | хуже на длинных текстах |

`base` — золотая середина: качество близко к OpenAI, работает offline, бесплатно.

### Префиксы query: и passage:

E5 — особенная модель. Её обучали с двумя ролями:

- **`query: вопрос`** — для коротких поисковых запросов
- **`passage: текст`** — для длинных документов

Это **обязательно** — без префиксов качество падает на 5–10%. В нашем коде:

```python
# При индексации (embed_resume.py)
тексты = ["passage: " + ч["text"] for ч in батч]

# При поиске (app.py)
вектор = модель.encode("query: " + вопрос, normalize_embeddings=True)
```

### normalize_embeddings=True

Эмбеддинги по умолчанию выходят с разной «длиной» — но для косинусного сходства длина не нужна, важно только направление. Параметр `normalize_embeddings=True` приводит каждый вектор к единичной длине (`||v||₂ = 1`).

После нормализации:

- Косинус двух векторов = их скалярное произведение (быстрее считать).
- Все векторы лежат на 768-мерной сфере.
- Qdrant с метрикой `Cosine` работает корректно.

### Что эмбеддинг «понимает»

- Синонимы: «авто» ≈ «машина» ≈ «car».
- Кросс-язычность: «вода» ≈ «water» ≈ «H₂O».
- Терминологию: «выход реакции» ≈ «reaction yield».

Что **не понимает**:

- Числа в формулах (для модели `Y = 0.95` и `Y = 0.05` почти одно и то же).
- Имена собственные (новые молекулы, авторы).

Поэтому RAG ≠ магия — нужна LLM поверх, чтобы интерпретировать найденные куски.

## 4. Qdrant: теория и практика (20 мин)

### Что такое векторная БД

Обычная БД хранит строки и ищет по точному совпадению/индексу. Векторная БД хранит **векторы** и ищет **по близости** в N-мерном пространстве.

Запрос: «дай мне 5 точек, ближайших к этому вектору». Выходит топ-K ближайших соседей — это и есть наши «релевантные фрагменты».

### Косинусное сходство

Метрика близости двух векторов A и B:

```
cos(A, B) = (A · B) / (||A|| × ||B||)
```

где `A · B` = скалярное произведение, `||A||` = длина вектора. Результат от −1 до 1.

| Значение | Смысл |
|---|---|
| **1.0** | идентичные векторы (одинаковый текст) |
| **0.85+** | очень похожие тексты (синонимы, парафраз) |
| **0.70–0.85** | связанная тема |
| **0.50–0.70** | слабая связь |
| **< 0.50** | разные темы |
| **0.0** | перпендикулярные (никак не связаны) |
| **−1.0** | противоположные (на практике не встречается у нормированных текстов) |

Для нормализованных векторов (`||A|| = ||B|| = 1`) формула упрощается:

```
cos(A, B) = A · B = sum(A[i] * B[i] for i in range(768))
```

Это просто скалярное произведение, считается за O(768) — миллионы раз в секунду.

В нашем коде задано `МИН_СХОДСТВО = 0.72` — фрагменты ниже этого порога не попадают в LLM. См. `app.py:287`.

### HNSW — алгоритм быстрого поиска

Если у нас 46 000 фрагментов, наивный поиск считает 46 000 косинусов на каждый запрос. Слишком медленно для интерактива.

Qdrant использует **HNSW** (Hierarchical Navigable Small World) — структуру, похожую на skip-list для графа. Поиск идёт за O(log N), на 46K точек — ~30 операций вместо 46 000.

Точность ~99% от точного поиска (мы можем пропустить 1 из 100 правильных ответов, но в обмен получаем 1000-кратное ускорение).

### Embedded vs Server режим

Qdrant работает в двух режимах:

**Server (production)**: отдельный процесс, общается через REST/gRPC, поддерживает реплики, шардирование.

**Embedded (наш режим)**: библиотека внутри Python-процесса, читает локальные файлы. Никакого сервера, никаких портов.

```python
клиент = QdrantClient(path="qdrant_db/")  # просто путь к папке
```

Плюсы embedded:

- Запуск одной командой `streamlit run app.py`.
- Работает без интернета и без отдельных процессов.
- Идеально для прототипа/демо/защиты диплома.

Минусы (нам не важны):

- Один процесс читает БД монопольно.
- Нет реплик/бэкапа из коробки.

### Структура коллекции

В нашей БД одна коллекция «химия». Каждая точка содержит:

```python
PointStruct(
    id=12345,                                # уникальный int
    vector=[0.12, -0.45, ..., 0.03],         # 768 float
    payload={                                # метаданные
        "text": "Выход реакции рассчитывается...",
        "document": "s13321-021-00577-1.pdf",
        "page": 3,
        "case": "выход_реакции"
    }
)
```

`payload` — произвольные JSON-данные, которые возвращаются вместе с точкой при поиске.

### Запрос с фильтром по кейсу

Если пользователь выбрал в селекторе «Прогноз токсичности», в Qdrant уходит запрос с фильтром:

```python
ответ = клиент.query_points(
    collection_name="химия",
    query=вектор_вопроса,
    limit=15,                       # k=5, берём 3× для запаса под фильтры
    query_filter=Filter(
        must=[FieldCondition(
            key="case",
            match=MatchValue(value="токсичность")
        )]
    ),
    with_payload=True
)
```

Filter работает как индекс: Qdrant сначала ограничивает поиск точками с `case == "токсичность"`, затем ищет ближайшие соседи в этом подмножестве.

### Как мы используем Qdrant

Главные операции (см. `app.py:259`):

1. **Embed запроса** — `модель.encode("query: " + вопрос)`.
2. **query_points** — поиск top-K ближайших.
3. **Чистка PDF-артефактов** в payload (`почистить_pdf_артефакты`).
4. **Порог релевантности**: `score >= 0.72`.
5. **Фильтр мусора**: `похоже_на_библиографию`, `похоже_на_мусор`.
6. **Срез** до запрошенного количества (по умолчанию 5).

Запас 3× (`limit=количество * 3`) нужен потому, что фильтры выкидывают часть результатов, и нам нужно остаться при 5 чистых фрагментах.

### Производительность

На моей машине (CPU без GPU):

- Embed запроса: ~50 мс.
- Qdrant search top-15: ~10 мс.
- Фильтры: ~1 мс.
- LLM (Groq): ~1.5–3 с.
- Итого: ~2–4 с от вопроса до ответа.

LLM — узкое место, всё остальное мгновенно.

## 5. Groq API и LLaMA 3.3 70B (10 мин)

### Что такое Groq

**Groq** — стартап, который сделал собственный чип LPU (Language Processing Unit), оптимизированный под inference больших моделей. Скорость — 500–1000 токенов в секунду, в 10× быстрее GPU.

Бесплатный тариф (наш кейс):
- ~14 400 запросов в день.
- Token-per-day лимит на каждую модель (TPD).
- Если упёрся в лимит → 429 Rate Limit.

### Модели в нашем проекте

| Модель | Контекст | Что делает |
|---|---|---|
| `llama-3.3-70b-versatile` | 128K | основные ответы пользователю |
| `llama-3.1-8b-instant` | 128K | резерв при TPD 70b, перевод фрагментов, извлечение формул |

LLaMA — открытая модель от Meta. 70B = 70 миллиардов параметров (большая, умная, но требует серверов). 8B — маленькая, быстрая.

### Почему LLaMA, а не GPT-4

| Параметр | Groq LLaMA 3.3 70B | OpenAI GPT-4 |
|---|---|---|
| Скорость | 500 ток/с | 50 ток/с |
| Цена | бесплатно (с лимитами) | $0.03/1K input |
| Доступ из РФ | прямой | через прокси/VPN |
| Качество (RU) | сравнимо | чуть выше |

Для учебного проекта Groq — оптимум.

### Как устроен вызов

Системный промпт + контекст + вопрос → ответ. См. `app.py:359`:

```python
ответ = вызвать_groq({
    "model": "llama-3.3-70b-versatile",
    "messages": [
        {"role": "system", "content": системный_промпт},   # 10 правил
        {"role": "user", "content": f"CONTEXT:\n{контекст}\n\nQUESTION:\n{вопрос}"}
    ],
    "temperature": 0.1,    # минимум креатива → меньше галлюцинаций
    "max_tokens": 1500,
})
```

Где `контекст` — это все 5 найденных фрагментов с метками:

```
[1] Документ: s13321-021-00577-1.pdf, стр. 3
Выход реакции (Y) рассчитывается как отношение фактически полученной массы продукта...

[2] Документ: paper2.pdf, стр. 5
В работе предложен метод предсказания выхода реакции на основе...

[3] ...
```

Цифры в скобках `[N]` — наши служебные маркеры. Модель должна их использовать в ответе как ссылки на фрагменты. Это и есть механика inline-цитат.

### Системный промпт — 10 правил

В `app.py:36-48` живут 10 жёстких инструкций модели. Самые важные:

| № | Суть |
|---|---|
| 1 | Только русский язык (даже если CONTEXT английский) |
| 2 | Только факты из CONTEXT, не выдумывать |
| 3 | Если есть хоть частичная информация — отвечать развёрнуто |
| 4 | `[N]` в CONTEXT — наши маркеры, **не** библиография. Не путать |
| 5 | Если CONTEXT не релевантен — сказать «В базе нет данных для ответа» |
| 6 | Термины оставлять в оригинале + русский в скобках при первом упоминании |
| 7 | **ОБЯЗАТЕЛЬНО** маркеры `[N]` после каждого утверждения. Не на связки |
| 8 | НЕ добавлять раздел «Источники:» в конец — мы выводим его сами |
| 9 | Главные формулы в `$$...$$`, inline `$...$` только для одной переменной |
| 10 | НЕ выдумывать формул, которых нет в CONTEXT |

Каждое правило родилось из конкретного бага. Например, правило 4 — потому что без него модель видела `[1] Документ:...` и думала «это библиография», и отказывалась отвечать.

### Двойной автофолбэк

Лимиты Groq могут закончиться → запрос падает с 429. Защита (`app.py:319`):

```
ключи = [GROQ_API_KEY, GROQ_API_KEY_2, GROQ_API_KEY_3]
модели = [llama-3.3-70b-versatile, llama-3.1-8b-instant]

для каждой модели:
    для каждого ключа:
        попробовать вызвать
        если 429 → следующий ключ
        если другая ошибка → пробросить
```

Логика: если у первого аккаунта закончился TPD на 70b → пробуем второй ключ → третий → откатываемся на 8b модель → её квота отдельная.

В реальности после 14 часов активного использования у меня заканчивался TPD первого ключа, но второй и 8b всегда выручали.

### temperature=0.1

LLM при генерации каждого токена выбирает из распределения вероятностей. `temperature` — мера хаоса:

- `0.0` — всегда самый вероятный токен (детерминированно).
- `0.7` — стандарт для креатива, разнообразия.
- `2.0` — почти случайный текст.

Мы ставим `0.1` — почти детерминированно, чтобы модель не «фантазировала». Для RAG это критично.

### Этап 2: ingest.py — извлечение и чанкование

Главный скрипт превращения PDF/DOCX в плоский JSON:

```bash
python ingest.py
```

Что происходит (см. `ingest.py`):

**A. Извлечение текста:**

```python
# PDF — через pypdf постранично
def извлечь_текст_из_пдф(путь):
    читалка = pypdf.PdfReader(путь)
    for номер, страница in enumerate(читалка.pages, start=1):
        текст = страница.extract_text()
        if текст and len(текст.strip()) > 50:
            страницы.append((номер, текст.strip()))

# DOCX — все параграфы + ячейки таблиц
def извлечь_текст_из_docx(путь):
    документ = docx.Document(путь)
    куски = [пар.text для пар in документ.paragraphs]
    куски += [...ячейки таблиц...]
```

DOCX не имеет понятия «страница» — режем виртуально по 2500 символов.

**B. Чанкование с overlap:**

```python
размер_чанка = 800
перекрытие = 100

def разбить_на_чанки(текст, размер, перекр):
    чанки = []
    начало = 0
    while начало < len(текст):
        конец = начало + размер
        кусок = текст[начало:конец]
        if len(кусок.strip()) > 80:
            чанки.append(кусок.strip())
        начало = конец - перекр   # шаг 800-100=700
    return чанки
```

**Зачем overlap (перекрытие 100 символов)?** Если предложение/формула попадает на границу двух чанков — без перекрытия её разорвёт пополам, и ни один чанк не будет содержать полной мысли. Overlap гарантирует, что важный кусок целиком попадает в один из чанков.

**Почему 800 символов?** Эмпирический баланс:

- Слишком маленький (200) → мало контекста, модель не понимает суть.
- Слишком большой (3000) → embedding «размазан», поиск менее точный + LLM-токены тратятся зря.
- 800 ≈ один абзац с формулой — оптимум для научных текстов.

**C. Авто-теггинг кейса:**

Для каждого чанка вызывается `определить_кейс(текст)` из `cases.py`. Считает количество ключевых слов из 15 кейсов и присваивает тот, у которого больше всего матчей. Дефолт — «компетенции».

**D. Сохранение в JSON Lines:**

```jsonl
{"text": "Выход реакции рассчитывается...", "document": "paper.pdf", "page": 3, "case": "выход_реакции"}
{"text": "Метод опорных векторов применяется...", "document": "paper2.pdf", "page": 7, "case": "поиск_молекул"}
...
```

JSON Lines (`.jsonl`) — формат «один JSON на строке». Удобно стримить большой файл без загрузки в память.

Результат: ~46 000 чанков из 575 документов, файл `chunks.jsonl` ~42 MB.

### Этап 4: app.py — основная логика

#### 4.1. Загрузка ресурсов с кэшем

```python
@st.cache_resource
def загрузить_модель():
    return SentenceTransformer("intfloat/multilingual-e5-base")

@st.cache_resource
def загрузить_qdrant():
    return QdrantClient(path="qdrant_db/")
```

`@st.cache_resource` — Streamlit-механизм: модель и Qdrant загружаются **один раз** при старте процесса, а не при каждом нажатии кнопки. Иначе ждали бы 10 секунд на каждый запрос.

#### 4.2. Поиск похожих фрагментов

`app.py:259` — функция `найти_похожие(вопрос, выбранный_кейс, количество)`:

```python
def найти_похожие(вопрос, выбранный_кейс, количество):
    модель = загрузить_модель()
    клиент = загрузить_qdrant()
    вектор = модель.encode("query: " + вопрос, normalize_embeddings=True).tolist()

    # Опциональный фильтр по кейсу
    если_фильтр = None
    if выбранный_кейс != "все":
        если_фильтр = Filter(must=[FieldCondition(key="case", match=MatchValue(value=выбранный_кейс))])

    # Запрашиваем 3× с запасом — фильтры выкинут часть
    ответ = клиент.query_points(
        collection_name="химия",
        query=вектор,
        limit=количество * 3,
        query_filter=если_фильтр,
        with_payload=True
    )

    # Чистка PDF-артефактов (¼→=, þ→+ и т.д.)
    for точка in ответ.points:
        точка.payload["text"] = почистить_pdf_артефакты(точка.payload.get("text", ""))

    # Порог семантической близости
    МИН_СХОДСТВО = 0.72
    релевантные = [т for т in ответ.points if т.score >= МИН_СХОДСТВО]

    # Двойной фильтр мусора
    содержательные = [
        точка for точка in релевантные
        if not похоже_на_библиографию(точка.payload["text"])
        and not похоже_на_мусор(точка.payload["text"])
    ]

    return содержательные[:количество]
```

#### 4.3. Фильтры мусора

**`похоже_на_библиографию`** (`app.py:70`) считает «маркеры цитирования»:

- `[12]`, `[15]` в скобках
- нумерованные списки `1. Smith J.`
- `et al.`
- DOI, https-ссылки
- даты `(2019)`
- инициалы авторов `Smith J.,`

Если суммарно ≥6 — это страница References, отбрасываем.

**`похоже_на_мусор`** (`app.py:156`) ловит:

- Колонтитулы журналов (`ISSN`, `Scientific and technical journal`, и т. д.).
- Метаданные титулок (`поступила в редакцию`, `corresponding author`).
- Конфликт интересов и благодарности.
- Списки литературы.
- Последовательности цифр (>45% — таблицы).
- Тексты с <40% «связных слов» (коды генов вроде `MW535279`).

Список `_МУСОРНЫЕ_МАРКЕРЫ` в `app.py:89-130` — расширили за время разработки до ~30 паттернов.

#### 4.4. Чистка PDF-артефактов

PDF-экстракторы часто ломают символы из-за CID-маппингов:

```
Y = m_факт / m_теор × 100%   →   Y ¼ m_факт / m_теор × 100%
                                     ^
                                     это должно быть "="
```

Список замен (`app.py:133-142`):

| Артефакт | Замена | Причина |
|---|---|---|
| `¼` | `=` | cmap-каша: 1/4 вместо знака равно |
| `þ` | `+` | исландский thorn вместо плюса |
| `ð` `Þ` | `(` `)` | исландские буквы вместо скобок |
| `\u00ad` | `` | мягкий перенос — мешает поиску |
| `\ufb01` `\ufb02` | `fi` `fl` | лигатуры |

Применяется к каждому фрагменту перед показом в тултипе и перед отправкой в LLM.

#### 4.5. Генерация ответа (Groq)

`app.py:350` — собирается контекст из 5 фрагментов с метками `[1]…[5]`, отправляется в LLaMA с системным промптом.

Ответ возвращается с маркерами вида:

```
Выход реакции рассчитывается по формуле[1]. Альтернативно его выражают через объёмы продукта и реагентов[2][3].
```

#### 4.6. Пост-обработка ответа

После Groq применяются три функции:

**1) `отрезать_источники(текст)`** (`app.py:463`)

Удаляет финальный раздел «Источники:», если LLM не послушалась правила 8 и всё-таки добавила свой список.

**2) `убрать_неверные_маркеры(ответ, фрагменты)`** (`app.py:374`) — наша главная защита от галлюцинаций.

Алгоритм:

1. Найти все `[N]` в ответе.
2. Для каждого маркера выделить «утверждение» — текст от ближайшей границы (`. `, `! `, `\n`, `, `, `; `, `: `) до маркера.
3. Закодировать утверждения в эмбеддинги (e5, префикс `query:`).
4. Закодировать все 5 фрагментов (`passage:`).
5. Посчитать матрицу сходств `[len(утв) × len(фрагментов)]`.
6. Для каждого маркера: проверить, является ли фрагмент N действительно ближайшим к утверждению.

Критерии «маркер плохой»:

```python
если_слабый                 = sim < 0.65          # фрагмент N вообще не про это
если_отстаёт_абсолютно     = sim < max_sim - 0.015  # есть фрагмент заметно ближе
если_отстаёт_относительно  = sim < max_sim * 0.97   # хуже max более чем на 3%
```

Если хотя бы один критерий истинен → маркер удаляется.

**Зачем это нужно.** LLaMA иногда путает номера: видит формулу в фрагменте 3, но пишет `[1]`. Без пост-проверки тултип покажет цитату из фрагмента 1, не имеющую отношения к формуле — пользователь подумает, что система врёт.

Эта функция полностью автоматическая, работает на каждом ответе, добавляет ~200 мс.

**3) `_вынести_маркеры_из_формул(текст)`** (`app.py:176`).

LLM иногда ставит маркер прямо внутри формулы:

```
$$\frac{m_{практ}[2]}{m_{теор}}$$
```

Streamlit рендерит `$$...$$` через KaTeX, который парсит содержимое как LaTeX и **съедает HTML-разметку** — наш `<span class="cite">` исчезает, маркер становится некликабельным сырым текстом.

Решение: до замены `[N]` на span регексом находим все формульные блоки и переносим маркеры за их пределы:

```
$$\frac{m_{практ}[2]}{m_{теор}}$$  →  $$\frac{m_{практ}}{m_{теор}}$$[2]
```

Теперь `[2]` снаружи формулы, KaTeX его не трогает, замена на span работает.

#### 4.7. Вставка кликабельных цитат

`вставить_цитаты_в_ответ(текст, фрагменты)` (`app.py:201`):

1. Срезает раздел «Источники:» если LLM добавила.
2. Вызывает `_вынести_маркеры_из_формул`.
3. Экранирует HTML (`<` → `&lt;`).
4. Регексом `\[(\d+)\]` находит маркеры и заменяет на:

```html
<span class="cite">
    [N]
    <span class="cite-tip">
        <span class="cite-doc">paper.pdf, стр. 3</span>
        <span class="cite-text">Выход реакции...</span>
    </span>
</span>
```

CSS из `дизайн.py` показывает `.cite-tip` при hover на `.cite`. На мобильных тултип фиксированно по центру экрана, на десктопе — в правом нижнем углу viewport.

#### 4.8. Условный показ блока «Источники»

Если в ответе ноль маркеров `[N]` → значит LLM отказалась использовать фрагменты («В базе нет данных»). Тогда блок «Источники» **не показываем** — иначе обманываем пользователя «вот источники к ответу», а ответа на самом деле нет.

```python
есть_маркеры = bool(re.search(r"\[\d+\]", ответ))
if есть_маркеры:
    дизайн.показать_источники_rag(фрагменты)
```

## 7. Что мы модернизировали (15 мин)

Все эти улучшения **родились из реальных багов**, которые мы видели на скриншотах в процессе разработки.

### 7.1. Защита от мусорного контента

**Проблема.** В тултипах и в LLM попадали страницы References (`[1] Smith J. // Nature. 2020.`), колонтитулы журналов (`ISSN 2306-9117`), таблицы с цифрами, последовательности кодов генов (`MW535279, AMP/CIP/S/CTX`). LLM пыталась на их основе писать ответ → отказывалась или галлюцинировала.

**Решение.** Двухступенчатый фильтр в `app.py`:

1. `похоже_на_библиографию` — считает плотность маркеров цитирования (≥6 → отброс).
2. `похоже_на_мусор` — список из ~30 паттернов колонтитулов и эвристики на доле цифр / связных слов.

Результат: чистые фрагменты в LLM, чистые тултипы.

### 7.2. Embedding-проверка маркеров

**Проблема.** LLaMA иногда писала `[2]` там, где должно было быть `[3]` — путала номера. Тултип показывал нерелевантную цитату — система выглядела «жульницей».

**Решение.** Функция `убрать_неверные_маркеры` (`app.py:374`) делает повторный embedding-замер для каждого маркера:

- Берёт «утверждение» перед маркером.
- Считает cos-sim с каждым из 5 фрагментов.
- Если фрагмент N не является ближайшим (или хотя бы в пределах 3% от ближайшего) — маркер удаляется.

Это второй уровень защиты после системного промпта. Промпт-уровень не справляется с такими тонкими ошибками.

Калибровка (после реальных скриншотов от пользователя):

- `абс_порог = 0.65` — фрагмент совсем не про утверждение.
- `дельта = 0.015` — допустимое отставание от лучшего фрагмента.
- `ratio = 0.97` — относительная граница (sim ≥ 97% от max).

Тройной критерий ловит как явные промахи, так и пограничные случаи.

### 7.3. PDF cmap-артефакты

**Проблема.** В цитатах: `yi¼f xi þ εi` вместо `yi = f(xi) + εi`. Формулы становились нечитаемы.

Причина — cmap-словари в PDF: при экспорте символы `=`, `+`, `(`, `)` маппятся в `¼`, `þ`, `ð`, `Þ` (исландские буквы), потому что в шрифте PDF их кодовые точки совпадают.

**Решение.** Функция `почистить_pdf_артефакты(текст)` с таблицей замен (`app.py:133-142`). Применяется ко всем фрагментам сразу после Qdrant.

### 7.4. Системный промпт — 10 правил

Промпт эволюционировал от 2 правил до 10. Каждое — реакция на конкретный баг:

| Правило | Какой баг исправляет |
|---|---|
| 1 | LLM отвечала на английском при английских фрагментах |
| 2 | Выдумывала факты |
| 3 | Отказывалась при частичной информации |
| 4 | Видела `[1] Документ:` и думала «библиография», отказывалась |
| 5 | Писала длинные отказы вместо короткого «нет данных» |
| 6 | Переводила термины (`SMILES` → `СИУЛЕС`) |
| 7 | Не ставила маркеры → невозможно было показать тултипы |
| 8 | Дублировала раздел «Источники:» в конце ответа |
| 9 | Писала формулы inline → они сливались в строку |
| 10 | Подставляла «известные» формулы из обучения вместо тех, что в CONTEXT |

### 7.5. Кликабельные цитаты с тултипами

**Проблема.** Маркеры `[1]`, `[2]` без интерактива — пользователь должен скроллить вниз и сопоставлять номера с источниками вручную.

**Решение.** Каждый маркер — `<span>` с тултипом, при наведении показывается:

- Имя документа + страница.
- Реальный фрагмент (до 800 символов).

На десктопе тултип фиксирован в правом нижнем углу viewport. На мобильном — по центру экрана. Прокручиваемый, с двойным hover-триггером (открывается на маркере, остаётся открытым при наведении на сам тултип).

### 7.6. Маркеры внутри формул

**Проблема.** LLM ставит `$$\frac{m_{практ}[2]}{m_{теор}}$$` — маркер внутри LaTeX-блока. KaTeX парсит и съедает HTML span'а — маркер становится некликабельным.

**Решение.** Регексом находим формульные блоки и переносим маркеры за их пределы (`_вынести_маркеры_из_формул`). Smoke-тест: 5 кейсов, все прошли.

### 7.7. Обработка отказа LLM

**Проблема.** Если LLM написала «В базе нет данных», но Qdrant вернул 5 фрагментов (низкого качества) — мы показывали блок «Источники: paper1.pdf, paper2.pdf...». Это вводило в заблуждение: ответа нет, но «вот источники для него».

**Решение.** Если в ответе нет ни одного `[N]` → блок «Источники» не показываем. Вместо него — серое объяснение: «Эти фрагменты найдены векторным поиском, но модель не нашла в них ничего применимого».

### 7.8. Двойной автофолбэк по ключам и моделям

**Проблема.** Лимит TPD одного ключа Groq на 70b исчерпывается за 3-4 часа активного использования. Защита диплома без интернета на этой модели — риск.

**Решение.** В `.env` поддерживаем 3 ключа (`GROQ_API_KEY`, `GROQ_API_KEY_2`, `GROQ_API_KEY_3`) — например, разные аккаунты. Функция `вызвать_groq` пробует все по очереди, при 429 переключается на следующий. Если все упёрлись на 70b — откатывается на 8b (квота отдельная).

### 7.9. Группировка источников по документу

**Проблема.** Если 3 маркера ссылаются на один документ → раньше выводили 3 одинаковые строки. Если 5 фрагментов из 2 документов — счётчик `01, 02, 03, 04, 05` не совпадал с маркерами `[1]`, `[2]`.

**Решение.** Источники группируются по `document`, в одной строке выводится список всех маркеров `[2, 3, 5]`, ссылающихся на этот документ. Имя файла — кликабельная ссылка на Google Scholar по поисковому запросу из имени.

### 7.10. Адаптивная вёрстка

(Не в фокусе — но кратко.) Все блоки адаптированы под мобильные через медиа-запросы: схлопывание гридов, горизонтальный скролл вкладок, фиксированные тултипы по центру viewport, увеличенные тач-зоны кнопок. Подробнее — в `дизайн.py`.

## 9. FAQ для защиты (5 мин)

### Зачем e5, а не OpenAI?

OpenAI требует прокси из РФ, платный, 1536-dim (тяжелее хранить). E5 — бесплатно, локально, 768-dim, многоязычная (RU+EN), точность сравнима. Для учебного проекта — оптимум.

### Почему Qdrant, а не Pinecone / Weaviate / FAISS?

| БД | Плюсы | Минусы |
|---|---|---|
| **Qdrant embedded** ✓ | один файл, без сервера, REST API, фильтры | новее экосистема |
| Pinecone | managed cloud | платно, требует интернет |
| Weaviate | GraphQL, hybrid search | требует докер |
| FAISS | быстрая, in-memory | без payload, без фильтров, нужно самому писать слой |

Для embedded-сценария Qdrant — самый удобный (Python + path к папке = всё).

### Как вы боретесь с галлюцинациями LLM?

**Четыре уровня защиты**:

1. **temperature=0.1** — модель выбирает почти детерминированно.
2. **Системный промпт** — 10 правил, явно запрещающих факты вне CONTEXT.
3. **Embedding-пост-проверка** — `убрать_неверные_маркеры` отсекает ошибочные ссылки.
4. **Тултипы** — пользователь сам видит реальную цитату при наведении, может проверить.

### Как работает ваш поиск технически?

Embedding-модель кодирует вопрос в 768-мерный вектор. Qdrant использует HNSW-граф для быстрого поиска K ближайших соседей по косинусному сходству. На 46 000 точек — 10 мс на запрос. Дополнительно фильтруем результаты по релевантности (≥0.72) и эвристикам мусора.

### Зачем chunk size = 800?

Эмпирически. Меньше — теряется контекст вокруг формулы. Больше — embedding «размазывается» (модель не понимает, на чём фокус), плюс LLM-токены тратятся впустую. 800 ≈ один абзац с формулой и комментарием.

### Зачем overlap 100?

Чтобы предложение/формула на границе чанков не разорвалось пополам. С overlap гарантируется, что любая фраза длиной ≤100 символов целиком есть хотя бы в одном чанке.

### Что если кто-то задаст вопрос не по химии?

LLM по правилу 5 ответит «В базе нет данных для ответа на этот вопрос». Дополнительно: в ответе не будет маркеров `[N]` → мы не показываем блок «Источники», только серое объяснение «эти фрагменты найдены, но не применимы».

### А если интернета не будет на защите?

Тумблер «Демо-режим» → используются 5 заготовленных ответов из `fallback_answers.py`, без обращения к Groq. Этого хватит для демонстрации UI и логики.

### Сколько стоит проект?

Прямые расходы — 0 рублей.
- Embedding-модель: open-source (Hugging Face).
- Qdrant: open-source, embedded.
- Groq: бесплатный тариф (14 400 запросов/день).
- Туннель: `localhost.run` бесплатный.

Опосредованно — ~150 МБ диска под `qdrant_db/`.

### Можно ли заменить LLM?

Да, без переписывания других модулей. В `app.py:359` поменять `model="llama-3.3-70b-versatile"` на любую другую (Groq, OpenAI, Claude, локальная Ollama). Промпт совместимый — все современные LLM понимают одинаковый формат.

### Можно ли добавить новые документы?

```bash
# 1. Положить новые PDF в all_pdfs/
# 2. Перегенерить chunks.jsonl
python ingest.py
# 3. Догрузить в Qdrant (только новые чанки!)
python embed_resume.py
```

`embed_resume.py` идемпотентен: считает, сколько уже в БД, добавляет только новые. Не нужно векторизировать всё заново.

### Какие ограничения?

- **Размер контекста LLM**: ~120 K токенов. У нас в запросе ~5 фрагментов × 800 = 4 000 символов ≈ 1 000 токенов. До лимита далеко.
- **Качество embedding на узкоспециализированной терминологии**: `multilingual-e5-base` обучена на общем корпусе. Для редких химических терминов точность чуть ниже, чем у специализированной BioBERT/SciBERT. Можно дотренировать, но для учебного проекта `base` достаточно.
- **Скорость поиска**: HNSW даёт ~99% точности. В 1 случае из 100 правильный ответ может быть упущен. На практике пользователь не замечает.
